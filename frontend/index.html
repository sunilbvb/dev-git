📖 Gitflow Strategy & Release Guide

1. Permanent Primary Branches

  • main: Stable production-ready code. Commits are tagged.
  • develop: Integration branch. Gathering place for completed features.

2. Supporting Branches (Temporary)

Type Source Merge Target Purpose
feature/vX.X.X/* develop develop Developing new features in isolation.
release/vX.X.X/* develop main & develop Preparing release; bug fixes & docs only.
hotfix/vX.X.X/* main main & develop Emergency fixes for critical prod bugs.
bugfix/vX.X.X/* develop develop Minor non-critical bug fixes.

3. Standard Lifecycle

  1. Initialize develop from main.
  2. Create feature/* from develop → merge back when done.
  3. Initiate release/* from develop.
  4. QA Testing on release → Merge to main (tag it) & develop.

4. Testing & Bug Management

Internal Testing Integration: Quality checks happen inside the release branch. Build appbundle/IPA from release branch. Tester bugs are resolved directly on release branch. Merge to main only after green signal.

Hotfix vs. Bugfix: Critical production bugs use hotfix/ (branched from main). Minor UI/typo fixes use bugfix/ (branched from develop, deferred to next release).

🚀 Git Release Workflow: v1.1.x

Option 1: The Terminal (Fast & Local)
git checkout main
git pull origin main
git tag -a v1.1.4 -m "Release version 1.1.4"
git push origin v1.1.4
Option 2: GitHub Releases (Formal & Public)
  1. Go to Releases in GitHub → "Create a new release".
  2. Type version (e.g., v1.1.4).
  3. Release Title: e.g. v1.1.4 - The UI Update.
  4. Generate release notes, polish with sections:
    • ✨ New features
    • 🐛 Bug fixes
    • ⚠️ Breaking changes
  5. Upload compiled APK/bundles → Click "Publish release".
